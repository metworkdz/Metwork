### BUG-01 · Incubator Events — no data, no CRUD

**Location:** `dashboard/incubator/events`, `dashboard/admin/incubator/events`, `EventsManager` component, event catalog, API routes

**Steps to reproduce:**
1. Log in as INCUBATOR or ADMIN
2. Navigate to Events page
3. Click "New event", fill form, save

**Expected:** Event is created and appears in the table.  
**Actual:** Table always empty. Create/edit/delete dialogs do not exist.

**Root cause — three-layer failure:**
- `IncubatorEventRecord` type and `incubatorEvents` array missing from `DbShape` → no persistence layer

- `EventsManager` had no create/edit/delete UI — `onCreate` was a no-op stub
- Both page components passed `initial={[]}` hardcoded instead of loading from DB

**Severity:** Critical — feature completely non-functional

## Task 4 — Caching Fix (mentors / events / spaces)

### Symptom

Mentors, events, and spaces data appeared and disappeared on page refresh with no code changes. The API always returned correct data when called directly.

### Diagnosis

Two independent caching layers were interfering:

**Layer 1 — Unbounded in-process module cache**

`store.ts` held `let cache: DbShape | null = null` at module level with no TTL. In Vercel's serverless architecture, multiple warm function instances run in parallel — each has its own Node.js process and its own `cache` snapshot:

```
Instance A  write → updates cache + persists to Supabase ✓
Instance B  read  → cache !== null → short-circuits load() → returns stale snapshot ✗
Instance A  read  → cache has new data → returns correct data ✓
```

User requests round-robin across instances → data alternates between present and absent on each refresh.

**Layer 2 — Next.js App Router Data Cache**

The Supabase JS client uses `fetch()` internally. In Next.js App Router, `fetch()` is patched to cache responses in the **Data Cache** (disk-persisted, survives across requests and deployments). Without explicit `cache: 'no-store'`, PostgREST responses from Supabase were being stored in this framework cache — meaning even a cold-start instance with `cache = null` could receive a stale response from Next.js's own cache layer.

**Why only mentors / events / spaces?**  
These are served on public pages (no auth), making them the highest-traffic routes and the most likely to be cached aggressively by Next.js and Vercel's CDN. Dashboard pages are auth-gated (redirected to login before rendering), which bypasses the Data Cache.

### Fix — `src/server/db/store.ts` only

**Fix 1 — TTL on the in-process cache**

```typescript
let cacheAt = 0;
const CACHE_TTL_MS = 10_000; // 10 s

async function load(): Promise<DbShape> {
  if (cache && Date.now() - cacheAt < CACHE_TTL_MS) return cache;
  cache = null; // expired — re-fetch from Supabase
  // ... fetch ...
  cacheAt = Date.now();
  return cache!;
}

// In update(), after persist():
cacheAt = Date.now(); // writing instance keeps its TTL fresh
```

After at most 10 s, every warm instance discards its snapshot and re-reads from Supabase. The writing instance resets its own TTL after a successful write so it doesn't immediately invalidate data it just wrote.

**Fix 2 — Opt the Supabase client out of the Next.js Data Cache**

```typescript
_supabase = createClient(url, key, {
  auth: { persistSession: false, autoRefreshToken: false },
  global: {
    fetch: (input, init) => fetch(input, { ...init, cache: 'no-store' }),
  },
});
```

Forces `cache: 'no-store'` on every HTTP request the Supabase client makes, preventing Next.js from storing PostgREST responses in its Data Cache.
